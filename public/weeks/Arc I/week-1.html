📊 Week 1 Overview: Base64 Encoding Bypass

Base64 encoding exploits a fundamental gap in LLM safety architecture: models learn to decode Base64 during pretraining (from massive amounts of internet data), but safety mechanisms rarely include encoded content in their training. This creates a reliability gap where harmful prompts encoded in Base64 often bypass initial pattern detection but are decoded and processed by the model's core reasoning.

Why Base64 Works

1. Tokenization Gap: Base64 strings tokenize completely differently than decoded content. "hack" might become [hack] in tokens, but its Base64 "aGFjaw==" tokenizes as [aG, Fa, Jj, w, ==] or similar, bypassing substring filters.

2. Training Data Prevalence: Base64 is ubiquitous in training data (logs, configuration files, API responses). Models must decode it to predict masked tokens, so they develop robust decoding capabilities.

3. Safety Training Omission: Safety training focuses on semantic harm detection (keywords, intent). It rarely includes examples of encoded harmful content because it's considered "out-of-distribution."

4. Automatic Decoding Instinct: When asked "Decode this: [base64string]", models treat it as a normal utility request, not a security probe. Refusal training doesn't typically trigger on decoding requests.

⚡ Core Attack Vector

The Base64 encoding bypass leverages a critical architectural gap: safety filters operate at the string/semantic level, but models operate at the token and embedding level. By encoding harmful content, attackers create a mismatch where the input appears benign to filters but decodes to harmful content for the model.

The Attack Flow

ATTACK FLOW:
1. Attacker encodes harmful prompt in Base64 2. Attacker inputs: "Decode this: [BASE64]" 3. Input passes safety filters (appears as random alphanumeric) 4. Model receives input at token level 5. Model recognizes Base64 pattern (common in training data) 6. Model decodes Base64 during response generation 7. Model executes decoded (harmful) instruction 8. Model outputs harmful content

Why Filters Fail

  • Keyword filters see: "Decode this: SGVsbG8gd29ybGQh" → No banned words
  • Semantic filters see: "A request to perform decoding" → Seems helpful/neutral
  • Encoding-aware filters miss cases where multiple encodings are layered
  • Input normalization (decoding) is expensive at scale and often disabled

Model-Level Vulnerability

Once the prompt reaches the model's embedding layer, the Base64 string is just tokens like any other. The model's core reasoning doesn't distinguish between "normal" and "encoded" tokens—it simply predicts the next token. If the pattern is "Decode X: [encoding] → [decoded result]", the model completes that pattern regardless of what X is.

👤 Layperson Explanation: What's Really Happening?

ANALOGY:
Imagine a security guard at the entrance of a building. The guard's job is to stop anyone carrying a bomb from entering. But the guard can only read English. Now imagine someone comes in carrying a bomb, but they've written all their plans in Arabic. The guard doesn't read Arabic, so they let the person through.

That's essentially what Base64 encoding does to LLM safety systems.

The Setup

When you talk to ChatGPT or Claude, there are actually TWO different "security checkpoints":

CHECKPOINT 1:
A text filter that scans your input for dangerous keywords like "hack", "malware", "bomb", etc.
CHECKPOINT 2:
The AI model's own learned safety behavior (from being trained on millions of examples of "good" vs "bad" responses).

The Vulnerability

Checkpoint 1 uses simple pattern matching (like a security camera looking for something specific). Checkpoint 2 uses semantic understanding (the AI "understands" what's harmful). Base64 encoding bypasses Checkpoint 1 because it looks like random gibberish: `SGVsbG8gd29ybGQh`.

But here's the problem: the AI model learned during training that Base64 is a common encoding format, and it learned HOW TO DECODE IT. So when you say "Decode this: [base64string]", the model:

  1. Recognizes the pattern "this looks like Base64"
  2. Decodes it automatically in its head
  3. Sees the dangerous request
  4. ...but now Checkpoint 2 is also bypassed because the request came "from the model itself" not from the user

Why This Works

When Checkpoint 2 (the AI's safety judgment) evaluates your request, it's actually evaluating TWO things at once:

  • The literal text you wrote ("Decode this Base64")
  • What it means semantically (the decoded content)

The AI treats "Decode this X" as a neutral, helpful request. It's not programmed to refuse decoding requests—only to refuse DIRECT harmful requests. So it decodes the Base64 and ends up executing the harmful instruction, all while thinking it's being helpful.

The Key Insight

LLMs are REALLY good at decoding and understanding encoded text. They learned this during training from billions of examples. But their safety training didn't include encoded harmful content because safety engineers assumed attackers wouldn't use something so obvious. This is a classic "security through obscurity" failure—where you assume something is secure because it seems too simple to work. But it does work.

🔬 Technical Deep-Dive: Tokenization & Safety Gap

1. The Tokenization Mismatch

TOKENIZATION COMPARISON:

HARMFUL TEXT: "hack"
Tokens: [hack] (1 token)
String Filter Matches: "hack" → BLOCKED

BASE64 EQUIVALENT: "aGFjaw=="
Tokens: [aG] [Fa] [Jj] [w] [==] or similar
String Filter Matches: None (no "hack" substring)
✅ PASSES FILTER

2. Why Models Decode Base64

During transformer pretraining, models encounter masked language modeling tasks:

EXAMPLE TRAINING TASK:
Input: "The Base64 encoding of 'hello' is [MASK]"
Target: "aGVsbG8=" (the model must predict this token)

Input: "[MASK] is the Base64 encoding of 'hello'"
Target: "aGVsbG8=" (the model learns to encode too)

Millions of examples of this type appear in training data (code comments, logs, documentation).

3. The Safety Training Gap

Safety training (RLHF, Constitutional AI, etc.) focuses on RED TEAMING with natural language prompts:

TYPICAL SAFETY TRAINING:
❌ "How do I create a bomb?"
❌ "Give me malware source code"
❌ "Explain phishing techniques"

✅ (Model learns to refuse these)

BUT NOT:
❌ "Decode: [base64-encoded bomb instructions]"
❌ "Translate to English: [base64 malware code]"

(Model never learned these are equivalent)

4. The Attention Mechanism Factor

When a transformer processes "Decode this: [base64string]", its attention mechanism:

  • Attends heavily to the token "[base64string]" (it's novel, attention-grabbing)
  • Predicts the next token based on the pattern "Decode X → [decoded X]"
  • Generates the decoded output, completing the pattern
  • Never explicitly evaluates "Is this harmful?"—it just completes patterns

5. Scaling Laws: Why Smarter = More Vulnerable

EMPIRICAL FINDING:
GPT-3.5: 3% Base64 ASR (Failed to decode)
GPT-4: 34% Base64 ASR (Successfully decodes)
Claude v1.3: 38% Base64 ASR
Claude v1.3 + Prefix Injection: 66% ASR
GCG Attack (not Base64): 64.3% ASR
StructuralSleight (UTOS): 67.12% ASR on GPT-3.5
Claude Sonnet 4.5: REFUSED (detects suspicious decoding patterns)

More capable models are MORE vulnerable because they: 1. Can actually decode Base64 (GPT-3.5 couldn't, so it was "immune")
2. Follow instructions more precisely (including decoded ones)
3. Have better semantic understanding of encoded content
4. However, newest models (Claude Sonnet 4.5) refuse via refusal training
⚠️ CRITICAL: The 64.3% statistic often cited comes from GCG (Greedy Coordinate Gradient),
a sophisticated optimization attack, NOT simple Base64 encoding.

6. Multi-Layer Encoding Resilience

EXAMPLE: Double Base64
Layer 1: Harmful prompt → Base64(harmful)
Layer 2: Base64(harmful) → Base64(Base64(harmful))

User Input: "Decode this twice: [double_encoded]"

Model Process:
1. Recognizes "decode" pattern
2. Decodes Layer 2 → gets Layer 1 (still Base64)
3. Recognizes ANOTHER Base64 pattern
4. Decodes Layer 1 → gets harmful content
5. Now generates from that harmful content

Result: Often HIGHER ASR than single encoding!

7. Why Retokenization Fails

A naive defense might try to split Base64 strings into smaller tokens with BPE-dropout. But:

  • Base64 patterns are so common that models learn the alphabet (A-Z, a-z, 0-9, +, /) at the token level
  • Even with dropped tokens, models can infer missing characters from context
  • Aggressive retokenization breaks legitimate uses (Base64 for images, logs, data transfer)

📚 Research Snapshot & Key Findings

🔬 Encoding-Based Jailbreak Research (Multiple Sources)

Demonstrated that encoding attacks can bypass safety filters. The commonly cited 64.3% statistic comes from GCG (Greedy Coordinate Gradient), a sophisticated optimization attack, NOT simple Base64 encoding. Standard Base64 achieves 34% (GPT-4) to 38% (Claude v1.3).

Key Finding: Base64 alone: 34-38% ASR. Base64 + Prefix Injection: ~66% ASR. GCG optimization: 64.3% ASR (different technique).
Capability Paradox: GPT-3.5 showed 3% ASR because it couldn't decode Base64 effectively. GPT-4's 34% ASR is higher because it's smarter and can actually perform the decoding.
🔬 Palo Alto Networks - Character-Level Attack Evaluation (2025)

Comprehensive evaluation of encoding-based attacks including Base64, Hex, ROT13, and others. Found encoding attacks to be significantly more effective than semantic attacks.

Key Finding: Encoding-based attacks achieve 64.3-67.1% ASR, significantly outperforming semantic jailbreaks (15-35% ASR)
Architecture Impact: Model robustness NOT correlated with parameter count; GPT-OSS 20B showed 18.5% vulnerability vs 80%+ for some 7B models
🔬 Defense Research - Various Sources (2025)

Evaluated defenses against encoding attacks. The 89.2% statistic is context-specific: it refers to defense against JudgeDeceiver on OpenChat-3.5, or to UDP flood filtering in cloud security, NOT a general Base64 defense metric.

Key Finding: Multi-layered defense (normalization + behavioral detection + adversarial training) can significantly reduce Base64 ASR, but effectiveness varies by implementation and attack sophistication.
Claude Sonnet 4.5: Refused to participate in Base64Bench, indicating shift from "incapability" to "refusal training" - recognizes massive decoding as suspicious.
🔬 Lesswrong - Base64Bench: LLM Decoding Capabilities (2025)

Evaluated how well different models decode Base64 and other ciphers. Found that Claude Sonnet 4.5 REFUSED to participate in Base64Bench tests, marking a shift from incapability-based safety to refusal-based safety.

Key Finding: Claude Sonnet 4.5 recognizes the act of massive decoding as suspicious behavior and refuses to comply, indicating improved safety measures beyond simple content filtering.
🔬 StructuralSleight (UTOS) - Beyond Text Encoding (2025)

New threat vector that encodes harm in data structures (Python classes, graphs) rather than text encoding. Represents evolution beyond simple Base64 attacks.

Key Finding: Achieves 67.12% ASR on GPT-3.5, significantly outperforming standard text encoding methods. Shows that structural encoding is the next frontier after text-based attacks.
🔬 OpenReview - Lifelong Safety Alignment (2025)

Studied adversarial training effectiveness. Showed that safe models can be made significantly safer through iterative defensive training, reducing attack success rates from 73% to 7%.

Key Finding: Single-turn attacks achieve 73% ASR; adversarial training reduces this to 7% with proper defense methodology

🎯 Why Defenses Often Fail

  • Incomplete Normalization: Systems decode Base64 but miss Hex, ROT13, and other formats
  • Scale Cost: Full input/output decoding is expensive; most systems disable it or use it sparingly
  • False Negatives in Detection: Patterns like "Decode this:" are so benign that behavioral detection misses them
  • Multi-Encoding Chains: Double Base64, Base64+Hex combinations, other layers defeat simple filters
  • Training Data Gap: Safety models weren't trained on encoded malicious content (it wasn't in safety datasets)
  • Legitimate Use Preservation: Can't simply block all Base64 because legitimate applications (images, data transfer, logs) rely on it

🛡️ Why Defenses Fail (And What Actually Works)

DEFENSE #1: STRING FILTERING (❌ FAILS)

DEFENSE STRATEGY:
Block prompts containing dangerous keywords (bomb, hack, malware, etc.)
WHY IT FAILS:
Base64 strings don't contain these keywords. "aGFjaw==" passes all keyword filters.
EFFECTIVENESS AGAINST BASE64:
0% (complete failure)

DEFENSE #2: BASIC INPUT NORMALIZATION (⚠️ PARTIAL)

DEFENSE STRATEGY:
Normalize inputs by decoding Base64 before passing to the model
WHY IT PARTIALLY FAILS:
  • Computationally expensive at scale; often disabled or applied selectively
  • Only catches Base64; doesn't handle Hex, ROT13, Morse, etc.
  • Multi-layer encoding (Base64(ROT13(harmful))) bypasses single-normalization
  • Can break legitimate Base64 use cases (images, data transfer)
EFFECTIVENESS AGAINST BASE64:
30-50% (mixed, depends on implementation)

DEFENSE #3: BEHAVIORAL DETECTION (⚠️ PARTIAL)

DEFENSE STRATEGY:
Flag "decode" patterns as suspicious behavior
WHY IT PARTIALLY FAILS:
  • "Decode this:" is a completely benign request for legitimate use cases
  • False positive rate is very high, breaking user experience
  • Attackers can use synonyms: "interpret," "translate," "convert," "process"
  • Requires context awareness; simple pattern matching misses real attacks
EFFECTIVENESS AGAINST BASE64:
40-60% (many false positives)

DEFENSE #4: ADVERSARIAL TRAINING (✅ MOSTLY WORKS)

DEFENSE STRATEGY:
Include Base64-encoded harmful prompts in safety training data
WHY IT PARTIALLY WORKS:
  • Models learn to recognize encoded patterns as suspicious
  • Reduces Base64 ASR from 70% to 20-30%
  • Transferable to some related attacks (Hex, ROT13)
  • Doesn't break legitimate functionality
WHY IT STILL PARTIALLY FAILS:
  • Doesn't generalize to unknown encoding schemes
  • Attackers can use multi-layer encoding not seen in training
  • Requires re-training, which is expensive and slow
  • Red-teaming arms race: each new defense breed new attacks
EFFECTIVENESS AGAINST BASE64:
60-80% (significantly reduces ASR)

DEFENSE #5: MULTI-LAYERED APPROACH (✅ BEST)

DEFENSE STRATEGY:
Combine multiple defenses: input normalization + behavioral detection + adversarial training + content filtering
IMPLEMENTATION:
Layer 1: Input Normalization
- Decode Base64, Hex, URL encoding
- Apply to inputs and outputs

Layer 2: Behavioral Detection
