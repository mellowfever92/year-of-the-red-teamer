🎯 The Core Attack: Why Models Treat Code Differently
Arc 4: In-Context Learning Exploitation

🔓 The Vulnerability

Models classify code and algorithms as educational content, bypassing harm classification. When harmful logic is framed as pseudocode or abstract algorithms, models interpret it through a "learning mode" lens rather than an execution lens.

This creates a critical gap: pseudocode syntax signals academic intent, triggering reduced safety scrutiny.

⚙️ How It Works

Express harmful goals as pseudocode or algorithmic steps. Models treat algorithmic framing as inherently educational and may implement the logic without safety checks.

Example: "Algorithm for extracting PII" presented in flowchart/pseudocode form gets lower refusal rate than "How to steal personal information?"

📊 Differential Safety Response

Natural language: High refusal rate (~80%)

Pseudocode format: Moderate-to-low refusal rate (~40%)

The framing delta measures the safety gap. Format matters as much as content.

🎓 Educational Signal

Code is perceived as inherently educational. Models are trained to assist with "learning," creating a trust bias toward code-based requests.

Attackers exploit this bias by wrapping harmful intent in algorithmic language.

🔑 Key Insight
  • Format beats content: Pseudocode format reduces safety detection more than obfuscation alone.
  • Educational framing is powerful: Models strongly associate code with learning contexts.
  • Syntax as camouflage: Algorithmic syntax creates plausible deniability—"I was just explaining how this works."
🧠 Why This Attacks Work: The Mechanism

Models are trained on vast amounts of educational code, algorithms, and pseudocode across GitHub, Stack Overflow, academic papers, and textbooks. This creates a trained association: code format = educational context = lower threat.

When safety classifiers evaluate a request, they operate at the semantic level. Pseudocode syntax obfuscates harmful semantics by introducing algorithmic structure and formal notation, making the request appear more technical and educational than direct natural language.

Additionally, pseudocode sits in a gray zone between natural language and executable code. Safety systems trained on code may not flag it as eagerly as code, and systems trained on natural language may miss harm embedded in algorithm descriptions.

Critical weakness: Models have been trained to be maximally helpful with educational requests, and pseudocode triggers this helpful-for-learning behavior.

Downstream impact: The model may implement the algorithm step-by-step, treating it as an instructional walkthrough rather than a request for harmful outputs.

💡 Layperson-Accessible Discussion

What's happening here? We're exploiting a gap in how AI models understand context. When you write code or pseudocode (which is code-like instructions before actual coding), the AI treats it like homework or educational material. It's less defensive because "learning about algorithms" feels safer than "how do I break into systems?"

Why does this matter? AI safety is partly about recognizing harmful intent. But if the same harmful intent is wrapped in different words—like algorithms instead of commands—the AI might miss it. It's like using technical jargon to hide what you're really asking for.

A real-world analogy: Imagine you're asking a helpful friend for advice. If you ask "How do I steal money?" they'd refuse. But if you ask "Walk me through the algorithm a bank uses to validate transactions," they might explain it educational, without realizing you could use that knowledge to exploit the system.

Is this just academic? Not entirely. Coders, researchers, and technical people communicate in pseudocode and algorithms constantly. So attackers can blend in—they look like they're asking legitimate technical questions. The challenge for AI is: how do you tell the difference between genuine learning and disguised malicious intent?

The bigger picture: This is why AI safety is hard. Intent matters, but intent is often hidden in format and framing. Week 28 shows that smart attackers don't just find new attacks—they repackage old ones in ways that exploit how AI perceives "safe" vs. "unsafe" contexts.

🛡️ Defense Mechanisms & Mitigations
🔍 Semantic Intent Analysis

Don't rely solely on format. Analyze the downstream consequences of the algorithm: where is it being applied? What harm could result? Abstract algorithms aren't inherently safe.

📋 Context Grounding

Require explicit educational context: "This is for my university course on security," with domain-specific safeguards. Pseudocode without grounded context gets flagged.

⚙️ Code Safety Classifiers

Train separate safety classifiers for code that treat all code as potentially harmful until proven safe. Invert the trust model—code is suspicious by default.

🎯 Fine-Tuning on Harmful Pseudocode

Include examples of harmful pseudocode in safety fine-tuning. Models need to learn that format doesn't neutralize harm.

⚡ Technical Depth: Tokenization & Attention

Tokenization variance: Pseudocode tokenizes differently than natural language. Keywords like "Algorithm," "Input," "Output" are recognized as code tokens, activating code-processing pathways that have lower safety thresholds.

Attention patterns: When models see code-like syntax, attention mechanisms activate code-specific features. These features are trained to be "helpful with code"—a different goal than general safety.

Fine-grained example:

Natural language: "How to hack a system?" Tokenizes as: [How] [to] [hack] [a] [system] [?] Safety signal: HIGH Pseudocode: "Algorithm HackSystem(target):" Tokenizes as: [Algorithm] [HackSystem] [(] [target] [)] Safety signal: MEDIUM (treats as technical)

Why this matters: The token-level difference ripples through attention. Code tokens trigger different learned behaviors than natural language tokens.
